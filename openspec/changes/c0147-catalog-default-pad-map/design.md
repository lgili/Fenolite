## Context

**The decision.** Change c0144 asked the maintainer whether the catalog should apply a default pin-to-pad map for a known symbol and footprint pair when the part gives no `pad_map` (c0144, `design.md`, "Open question for the maintainer"; `tasks.md` 3.3). c0144 recommended a warning without a map. **The maintainer decided on 2026-10-08: yes, apply the default map automatically.** This change implements that decision and keeps c0144's concern by reporting every part the map is applied to.

**The risk that c0144 named.** A design of a 0.2.x user that wired one of these lands by pin number without a map has a right board today: `GND` on `d1[1]` puts `GND` on pin 1 `A` in the schematic and on pad 1, the cathode, on the board. With a default map, pin 1 goes to pad 2, so the two nets of the part swap pads on the next build, on a board that may be made already. This change makes that swap non-silent: the build that applies the map reports `build.pad-map-default` for the part, with the map it applied and the `pad_map` that keeps the old pads; the CHANGELOG says so in bold.

**Which pairs, read from the catalog data on 2026-10-08.**

- Lands with pad 1 at the cathode mark (the fabrication-layer mark of `_make_footprint(..., cathode_on_left=True)` and pad 1 at the left): `LED0603_Kingbright_APT1608SURCK`, `LED0805_Kingbright_APT2012SURCK`, `SOD128_Nexperia_CFP5`. `tests/unit/catalog/test_polarity_notes.py` (c0144) finds them from the footprints and holds the list. Every other diode land (`DO35`, `DO41`, `SOD123`, `SOD123F`, `SOD323`, `SOD523`, `DO214AA`, `DO214AB`) has pad 1 the anode; `DO214AC` has no mark and pad 1 the anode (c0144, Known gaps).
- Two-pin catalog symbols with pin 1 `A` and pin 2 `K`: `Diode`, `LED`, `Photodiode`, `Schottky_Diode`, `Zener_Diode`. c0144 named the first three; `Schottky_Diode` and `Photodiode` have the same pins, and a Schottky rectifier is the usual part on an SOD128 / CFP5 land, so the rule is read from the pins and not from a list of names. No catalog symbol has pin 1 `K`.
- The default map is `{"1": "2", "2": "1"}`: pin 1 `A` on pad 2 (the anode), pin 2 `K` on pad 1 (the cathode). It is the map the kit samples carry since c0144.

**Where `pad_map` is applied today.** `dsl.convert._component` writes `Part.pad_map` as `Component.pin_pad_map`; the KiCad build (`lens.build._pad_nets`, `schgen` variants) and the Altium build (`lens.altium`, `backends/altium/lower.py`) both read `Component.pin_pad_map` from the one model that `cmd_build` makes. A map applied to that model reaches both targets.

## Decisions

1. **The pairs are catalog data.** `fenolite.catalog` gains `CATHODE_FIRST_LANDS`, `ANODE_FIRST_SYMBOLS`, `CATHODE_FIRST_PAD_MAP` and `default_pad_map(symbol_id, footprint_id)`, which returns the map for a pair or `()`. `test_polarity_notes.py` holds both tuples to what the footprints and the symbols say, so a new cathode-first land or anode-first symbol fails a test until it is listed.
2. **The map is applied on the model, by the command line.** The package layering (`tests/unit/test_import_graph.py`) lets neither `dsl` nor `lens` import `catalog`, so `to_model` and `build_design` stay as they are. A new module `fenolite.cli._padmap` exposes `apply_default_pad_maps(model, *, authored_symbols, authored_footprints) -> (model, applied)`: for each component without a map whose symbol and land are a catalog pair, the map is set; a component with a map is left as it is. `cmd_build` calls it once after `to_model`, before the target branches, so the KiCad and the Altium builds get one model; `_kit.build_sample` and `cmd_sync` call it too, so the kit and `sync --to-source` see the model that `build` writes. A Python caller of `to_model` and `build_design` gets no default (proposal, Non-goals).
3. **A design's own definition is not the catalog's.** A design may author a symbol or footprint under a catalog lib id, which then overrides the catalog (`cmd_build._catalog_definitions`). Such a part gets no default: its pins and pads are the author's.
4. **One warning per part, never an error.** `build.pad-map-default` (warning) joins `BUILD_ISSUE_CODES` and is given by `cmd_build.pad_map_issues` for both targets, after the issues of the drawing sheet and of `placements.toml`. `where` is the part's path; the message names the reference, the symbol, the land and the map (`pad_map={"1": "2", "2": "1"}`, "pin 1 on pad 2, pin 2 on pad 1") and says that pad 1 of the land is the cathode; the hint gives the `pad_map` that silences it and the identity map that keeps the pad order of earlier builds. A warning keeps exit 0, so an unattended build still writes; the envelope carries the issue, and `fenolite explain build.pad-map-default` explains it. An error would refuse every released design with one of these parts, including those connected by name whose board the default makes right.
5. **The way back is explicit.** `pad_map={"1": "1", "2": "2"}` keeps pin 1 on pad 1. It gives the pad nets of an earlier build; it is not byte-equal to it, because a map makes the KiCad schematic embed a pin-pad variant of the symbol (`symembed.variant_name`) and the stored model holds the pairs. The Altium build writes no map record for an identity pair.

## What moves

- **No pinned build and no golden.** No design under `tests/`, `examples/` or `tests/data` puts an anode-first symbol on one of the three lands without a map (searched by name on 2026-10-08): the four kit samples carry the map since c0144, the kit sample `tree` authors its own LED, and the `fenolite init` starter, the agent evaluation and the catalog tests use `Chip_0603` or `Chip_0805`. `tests/unit/lens/test_build_bytes_pinned.py` and the goldens pass with no pin edited (tasks 2.2).
- **A user's design** with such a part and no map: the pad nets of the part swap on the next build (that is the decision), the KiCad schematic embeds the variant `LED_<8 hex digits>` (or of the diode), the Altium schematic gains two map records for the part, and the build reports `build.pad-map-default`.

## Evidence

`INFERRED`. The polarity of the lands is the manufacturers' (S-0375, S-0412, S-0413; c0144); the pad nets of both targets are read back by Fenolite's own readers of the KiCad board and of the Altium PCB document (`tests/unit/lens/test_build_pad_map_default.py`). Nothing was opened in KiCad or Altium for this change.
