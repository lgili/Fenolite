## Context

- **Scope.** Plan D10, row v0.2b: "complete lens: `extract` + `adapt` + `moved()`; `sync --to-source` writes `placements.toml`; an orphaned complement becomes an issue. Acceptance: move 5 footprints and route 3 tracks in the GUI, add a part and rename a module with `moved()` → 100 % preserved". Plan v0.2b acceptance: "the lens test (D10) 100 % preserved, also in the fixture 'after *Update PCB from Schematic*'". Plan D1.6, authority table: for a project authored in Fenolite the layout's truth is the KiCad project, `.fenolite/` is a regenerable cache, and `placements.toml` is "the only extra source, committed, generated by `sync --to-source` (v0.2b)". Plan's package tree: `lens/` holds "v0.1 preserve.py; v0.2b extract.py, adapt.py, moved.py, sync.py".
- **The lens vocabulary.** The plan borrows it from the lens literature: the *view* is the Python script, the *complement* is the board. `extract` reads the view's data out of the complement, `adapt` (put) writes the view into the complement, and `moved()` tells the lens that a key changed.
- **What exists (c0019, archived on 2026-10-02, and its successors).**
  - `lens.preserve`: `match_footprints` with the keys uuid, then `fenolite.path` property, then alias (`moves`: new part path → old part path); `effective_placements` with locked `place()` > board > `place()` > staging; `merge_layout`, which keeps a footprint node for the keys uuid and path and re-places every alias match (`layout.alias-used`); copper kept by net name; zone fills kept while two text digests are equal; `merge_rules`; the closed table `PRESERVE_ISSUE_CODES`; `result.preserved`.
  - `Design.moved(old, new)` and `dsl.moves(design)`: component paths only. c0019's design, Decision 17: "Component paths only; module-prefix aliases and `lens/moved.py` are v0.2b". Its non-goals: "Net renames (a net alias), module-prefix aliases, and a three-way merge with a stored base (v0.2b sync)". `docs/lens.md`: "A renamed net therefore loses its routing; a net alias comes later".
  - c0011's `embed`: every uuid inside a placed footprint is `placement_uuid(<component path>, <locator>)`, and group `members` inside a definition follow the new values (`embed._uuids`).
  - `dsl.placements(design)` gives `Placement(at, rotation, side, locked)` in the written frame: `BOARD_ORIGIN` = (100 mm, 100 mm) plus the `place()` position.
  - Nets of a DSL design always have script names (`Net(name)`); a module-local net is named by the script, for example `Net(f"{m.path}/FB")` (`design-dsl`, "Design structure and names"). A component path and a module path never collide: both are refused as duplicates.
  - `tests/_layout_edit.py`: `move_footprint`, `add_items`, `net_ref`, `pad_position`, `edit_blink`.
  - KiCad 10.0 re-saves a board with `pcb upgrade --force` (S-0022), the stand-in for a GUI save; 9.0 has no such command (S-0037). `H-K-LENS-KEEP` is `KICAD-VERIFIED` on both majors for one moved footprint and one routed net.
- **v0.2a, proposed.** c0061 writes `<name>.kicad_sch` from `build`, puts `fenolite.path` on symbols, reads `schematic-placements.toml` (`lens.schplacements.read_placements`), replaces an edited schematic with `build.schematic-replaced`, and adds the stand-in `tests/_layout_edit.py::update_from_schematic` (`layout-lens`, "Boards updated from the schematic keep their layout"). Its design says "v0.2b's `sync` may write `schematic-placements.toml`". c0060 reads schematics (`sch.read_schematic`).
- **Constraints.** Stdlib only. `lens.*` imports only the standard library, `core`, `model` and `backends`, never `geometry`, `dsl` or `lens.build` (`package-layering`). No model entity, schema or id prefix changes. Integers only. No float in the files Fenolite writes.

## Goals / Non-Goals

**Goals:**
- Renaming a part, a module or a net in the script keeps everything done in KiCad that the rename does not invalidate.
- The layout can be rebuilt from the source tree alone: the script plus `placements.toml`.
- An agent can ask, before a build, what that build would drop and where the board and the script disagree.
- The plan's acceptance, run as a test on both majors.

**Non-Goals:**
- Everything under "Non-goals" in the proposal.
- Routing in the source tree. Tracks live in the board; `placements.toml` holds placements only.

## Decisions

1. **Module names follow the plan, without renaming `preserve.py`.** New modules: `lens/moved.py` (alias resolution), `lens/extract.py` (complement → view), `lens/placements.py` (the file), `lens/sync.py` (the sync plan). The adapt step is `lens/preserve.py`, which c0019 wrote; renaming it would change a living requirement and every import for no behaviour. `lens/__init__.py`'s docstring maps the plan's four names to the modules.
   - Rejected: `adapt.py` as a re-export of `preserve` (two names for one thing).

2. **Module aliases are `moved()` on module paths.** `Design.moved(old, new)` keeps its checks at the call. `dsl.moves(design)` returns the part aliases, now expanded:
   - when `new` is a component path of the design, the alias is a part alias, as today;
   - when `new` is a module path of the design, the alias is a module alias: every part path `new/<rest>` gets the alias `old/<rest>`;
   - a part alias wins over a module alias for its part, and a longer module path wins over a shorter one, so a module rename and a part rename inside it can be written together;
   - `old` MUST NOT be a component path or a module path of the design, and a chain stays refused.
   - `dsl.module_moves(design)` returns the module aliases (new module path → old module path), for the nets and for `result.preserved`.
   - Rejected: a separate `moved_module()` (the plan says "rename a module with `moved()`", and the path namespaces cannot collide). Rejected: a trailing `/` to mark modules (easy to forget, and no ambiguity exists).

3. **Net aliases.** `Design.moved_net(old, new)` records that the net now named `new` was named `old`; `dsl.net_moves(design)` returns them, new → old. `new` MUST be a net of the design and `old` MUST NOT be, and chains are refused, by the rules of part aliases.
   - A module alias also gives net aliases: `lens.moved.resolve_aliases` maps each board net `old/<rest>` that is not a design net to the design net `new/<rest>`, when it exists. An explicit `moved_net()` wins.
   - Rejected: guessing a rename from equal pin sets. A net split or merged in the same edit would move copper to the wrong net without a word.

4. **An alias match keeps its board node, under the new identity.** A footprint matched with key `alias` is kept when the library footprint and the placement are unchanged, the same rule as for the keys uuid and path. The identity map of the part is `{placement_uuid(old, loc): placement_uuid(new, loc)}` for every locator `loc` of the built copy's node. Then:
   - every `uuid` in the kept node whose value is a key of the map takes the mapped value; a uuid that KiCad gave an item added in the GUI is not a key and stays;
   - the `fenolite.path` property takes the new path, and the footprint's `path`, `sheetname` and `sheetfile` children take the built copy's values when the built copy has them (c0061, c0070);
   - every `members` atom of a root `group` node whose value is a key takes the mapped value (Decision 6).
   - Why rewrite the uuid instead of keeping the old one: a part later added at the old path would have the old uuid, and the uuid key, tried first, would match it to the renamed footprint. With the rewrite, an alias is needed for one build only, as c0019 intended, and "Rename through an alias" keeps its outcome.
   - A rename with a new library footprint, a locked `place()` or an off-board footprint is still re-placed, with `layout.alias-used`.
   - Fields: `merge_fields` treats the node as kept ("Footprint fields across rebuilds").

5. **Net aliases in the merge.** "Copper items follow their nets" keeps an item whose net name is the old name of a resolved net alias, and gives it the new net. Board-only footprint pads on that net follow too. One `layout.net-alias-used` (info) per alias gives the counts; an explicit alias that matched no item gives `layout.net-alias-unused` (warning).
   - The fill digests of the existing board are computed after its net names are mapped through the aliases. A pure rename then keeps fills: `fill_inputs_digest` enters nets by name, and a fill polygon does not hold its net. A rename that also moves a pin changes the digest and drops the fill, as today.

6. **Group members follow.** KiCad groups are opaque root children, kept unchanged by "Board content outside the design is kept". The one exception: member atoms named by an identity map. A group is otherwise never written by Fenolite.
   - DRC exclusions in the project file can also name a footprint's uuid. They are not rewritten here (Open Questions); `docs/lens.md` says that an exclusion of a renamed footprint has to be made again.

7. **`placements.toml`.** `lens.placements` reads and writes it; `tomllib` with `parse_float=Decimal` reads it, and Fenolite's own printer writes it, because the standard library has no TOML writer.
   ```toml
   # Written by fenolite sync --to-source.
   schema = "fenolite.placements.v0"

   [part."power/R1"]
   x = 12.7
   y = 30
   rotation = 90
   side = "top"
   locked = false
   ```
   - `x` and `y` are millimetres in the frame of `place()` (the written position minus `BOARD_ORIGIN`), whole nanometres; `rotation` is degrees in [0, 360), whole microdegrees; `side` is `top` or `bottom`; `locked` is the footprint's lock in KiCad, which gives the entry no precedence.
   - Tables under `part` keep a component path from colliding with the `schema` key.
   - The printer writes tables in component-path order, numbers in their shortest exact decimal form, and nothing that depends on the clock or the machine. Reading what it wrote gives the same entries.
   - Rejected: JSON (the plan names TOML, and a person edits this file); positions in the written frame (a reader would have to know `BOARD_ORIGIN`).

8. **Precedence with the file.** `effective_placements(…, source=…)`: locked `place()`, then the board, then the file, then `place()`, then staging. A file entry that wins is given as a `KeptPlacement` with the entry's lock, so `build_design` writes that lock, and `locked` never means "precedence" for it.
   - Without an existing board, and with `--discard-layout`, the same function runs with an empty match, so the file still wins over an unlocked `place()`. The file is source, like the script: deleting it is how a user drops it.
   - `layout.source-stale` (info): an entry differs from the kept board placement; the hint is `fenolite sync --to-source`. `layout.source-unknown` (warning): an entry names no part. `layout.place-overridden` now also covers an unlocked `place()` that a file entry overrides.

9. **Extraction skips footprints off the board.** `extract_placements` gives an entry for each matched footprint on the board and lists the others under `unplaced`. A staged part copied into the file would look placed and would lose its `layout.unplaced` warning.

10. **`fenolite sync DESIGN --out DIR --to-source [--check]`** (`mutates=True`).
    - Steps: run the script; read `DIR/<name>.kicad_pcb` (missing: `FEN-3001`, hint "build first"); resolve aliases, match footprints, extract placements and print `placements.toml`; when `DIR/<name>.kicad_sch` exists and c0060's reader is present, read every sheet of it and print `schematic-placements.toml` (Decision 11).
    - Writes go to the script's folder, one planned write per file whose text changes, through the mutation protocol.
    - `--check` writes nothing: one `sync.would-change` (error, exit 5) per file that would change, naming its first differing table. CI runs it to keep the committed file current.
    - Issues of the complement: `sync.orphan` (warning, the next build removes this footprint), `sync.net-dropped` (warning, the next build drops the copper of this net), `sync.value-differs` (warning: the board's value, footprint or user property differs from the script's, and the next build writes the script's). This is the plan's "an orphaned complement becomes an issue", raised before the build that would drop it.
    - Rejected: writing `placements.toml` from every build. The plan makes it the output of `sync`, and a build that writes into the source tree would surprise every user.

11. **Symbol placements from the schematic.** `lens.schplacements.extract_symbol_placements(sheets, *, design)` gives each symbol unit with a `fenolite.path` property its position, rotation and mirror, keyed as c0061's file is (`<path>` or `<path>#<unit>`). A position off the 1.27 mm grid, or a rotation and mirror pair outside `schlayout.PROVED_FRAMES`, gives `sync.symbol-off-grid` (warning) and no entry. `write_placements` prints the file that c0061's reader reads.
    - A schematic edited in KiCad is still replaced by the next build (c0061); `sync` is how its symbol moves reach the source first.

12. **The acceptance fixture.** `tests/data/lens/acceptance/design.py`, authored for Fenolite from the Mini library: modules `power` and `io`, a part `U1` at the top, module-local nets named from `m.path`.
    - Edits by token edit, standing in for the GUI: five footprints moved (`move_footprint`), three tracks with version-4 uuids on three nets, one of them `power/FB`, the `Reference` field of a `power` footprint moved, and a group holding two `power` footprints; then `update_from_schematic` when c0061 is present.
    - Script edits: a part `R9` added to `io`; `power` renamed to `supply` with `d.moved("power", "supply")`.
    - "100 % preserved" is checked item by item: the five placements, the three tracks (uuid, ends, width, layer, net under its new name), the field and the group, each equal after the identity map; no `layout.orphan`, `layout.net-removed` or `layout.footprint-replaced`; `R9` staged; a second build without the `moved()` call writes the same bytes.
    - Then `sync --to-source` and a `--discard-layout` build into a new folder put every footprint that was on the board where the edited board had it.
    - On KiCad: `H-K-LENS-RENAME` (kicad-oracle, "Renamed footprints pass the oracle").

13. **Cut order.** First the acceptance fixture's KiCad half (tasks 7.2, 7.3), then the schematic half of `sync` (task 5.3), then `--check` (task 5.2), then net aliases from module aliases (task 2.2, leaving explicit `moved_net()`). Never cut: kept alias matches, `placements.toml` and `sync --to-source` for the board, which are the plan's acceptance.

## Risks / Trade-offs

- [An identity map misses a uuid that KiCad moved to another item] → only exact values from the built copy's locators are mapped; anything else stays, and the oracle case compares DRC reports before and after.
- [A module alias maps a net that the user meant to drop] → only board nets that are not design nets are mapped, only to design nets that exist, and each mapping is reported (`layout.net-alias-used`).
- [The file and the board drift apart] → `layout.source-stale` on every build, and `sync --check` in CI.
- [A hand-edited `placements.toml` with a bad value] → `layout.source-invalid` (error), nothing written; the message names the table and the key.
- [Group rewrite in an opaque node] → limited to `members` atoms equal to a mapped uuid; the 10.0.6 re-save case checks that KiCad keeps the group.
- [`sync` on a board that KiCad 10 saved, for a target-9 design] → the reader's refusals of "Existing project files" apply unchanged.

## Migration Plan

- Additive for scripts: `moved()` on part paths, builds without `placements.toml` and boards without aliases behave as before, byte for byte.
- One behaviour change: a footprint matched through an alias with an unchanged library footprint and placement is now kept, so its GUI edits survive. "Rename through an alias" keeps its outcome (new uuid, new path, `layout.alias-used`, identical second build); `result.preserved` lists the part under `kept` instead of `replaced`.
- c0061 not archived when this change starts: the schematic half of `sync` and the stand-in step of the fixture wait, and the task says so.
- Rollback: remove `sync` and the file reader; alias matches go back to re-placement.

## Open Questions

- **Should DRC exclusions in the project file follow a renamed footprint?** Default: no, in this change. Their stored form differs between majors and is not measured; a probe can add it later without an interface change.
- **Should `sync` also write `placements.toml` for staged parts at their staged positions?** Default: no (Decision 9).
- **Should `--discard-layout` ignore `placements.toml`?** Default: no; the file is source. A flag can be added if users ask.
