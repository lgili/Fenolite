experimental too: what they keep is measured with KiCad and Fenolite's own readers, and Part T in Altium
Designer is open.

## Recorded limits

- **Deferred tasks.** No evidence label of a deferred task was raised: the rows named under "Deferred to
  the next release" and the entries of "Open changes of earlier releases" keep the level their change
  recorded.
- **Conversions.** Every direction is `experimental`; a conversion whose read-back differs from its source
  outside the direction's profile ends with exit 5 and names the difference. The census counts are in
  `docs/evidence/conversion.md`.
- **Slots.** Overlapping slots and cut-outs are merged through the `geo` extra; without it they are refused
  with a named code. Slots are not written to Altium in `0.5.0` (c0168).
- **The yardstick.** No scheduled run is recorded since `0.4.0`; its budgets and ratchets stay provisional.
- **Residue scan.** The residue scan of v0.5.0 ran with the public gate only, in CI and over the history;
  the private gate was not run for v0.5.0.

## Release build

release workflow's checkout, a fresh clone of the tag, or a worktree of it.

```bash
git worktree add "$TMPDIR/fenolite-v0.5.0" v0.5.0
cd "$TMPDIR/fenolite-v0.5.0"
uv build --out-dir dist
uv build packaging/phenolite --out-dir dist
```

## Maintainer's steps

Only the maintainer does these, or the coordinator at his word, in this order:

1. Read the checks of the release branch and of its pull request to `main`; the coordinator writes their
   runs in place of the placeholders above and closes the pending tasks whose proofs passed.
2. Read the rows, the deferred tasks and the open changes of earlier releases, and write the verdict below.
   A verdict other than `pending` is refused by the guard while a row is `pending` or a placeholder stands.
3. Merge the pull request from `dev` to `main` (the release branch) when its checks pass.
4. Tag `v0.5.0` on the merge commit.
5. Build from the tagged commit in a clean checkout: the commands of "Release build", or the release
   workflow, which builds from its own checkout of the tag.
6. Publish: the GitHub Release starts the release workflow, which uploads both packages (its publish step
   skips a version that PyPI already holds).
7. Archive c0171 with the verdict, and the changes of the release in the order of "Archive order" when each
   can be.
8. Merge `main` into `dev`.
