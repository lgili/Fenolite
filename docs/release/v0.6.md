# Release record: v0.6

What the release `0.6.0` ships, change by change: what each change ships, the test that proves it, in
which CI job, which of its tasks are still open and why. `0.6.0` is what `dev` implemented after `0.5.0`:
the MCP server and `fenolite edit` (c0195, c0196), the board engineering tools of c0175 and the changes that
implement its packages (c0197 to c0214, c0223 to c0229), the computed pours of Altium documents (c0215,
experimental), the release from a tag (c0221), the reliability, viewer-review, catalog and presentation work
(c0232 to c0240), the measured start of the Altium edit sessions (c0241, kit Part J) and the net roles
and their checks, phase 0 of the intent router (c0222, placed in `0.6.0` by the maintainer on 2026-10-29). A row says `ships`,
`ships with deferred tasks` or `pending`. The verdict at the end is the maintainer's.
`tests/unit/test_release_record_v06.py` keeps this page honest about what exists.

**The maintainer's decision of 2026-10-29.** He holds the v1.0 freeze: its five changes c0216 to c0220 stay
open and are not implemented for this release. `0.6.0` is released now with what is implemented since `0.5.0`,
and a `0.7.0` with improvements follows, its scope to be decided by him. The rule of his decision of
2026-10-08, kept on 2026-10-25, still holds: what depends on his own tests (checks in Altium Designer, KiCad
GUI saves made by him, a run of a real AI agent, his own MCP client) is deferred, the code of its change
ships, and no evidence label is raised for it. Nothing is held.

## Release build

The artefacts are built from the tagged commit in a clean checkout, never from the working tree: the
release workflow's checkout (`.github/workflows/release.yml`, change c0221), a fresh clone of the tag, or a
worktree of it.

```bash
git worktree add "$TMPDIR/fenolite-v0.6.0" v0.6.0
cd "$TMPDIR/fenolite-v0.6.0"
uv run --no-project python tools/release.py check --tag v0.6.0
uv build --out-dir dist
uv build packaging/phenolite --out-dir dist
```

History scan, on 2026-10-29 at commit `ab73da4` of `dev-c0241-b`: `uv run python tools/residue/scan.py
--history` read 6991 blobs of the local refs with the public gate and reported 0 hits; the private gate was
not run. The row `v0.6.0` of `docs/evidence/residue-history.md` holds it.

## Maintainer's steps

Only the maintainer does these, or the coordinator at his word, in this order:

1. Read the checks of the release branch and of its pull request from `dev` to `main`; the coordinator
   writes their run in place of the placeholder above.
2. Settle the history of the GitHub repository before the tag: the release workflow's step "Residue scan
   over the history" reads every ref, and c0220 task 1.2 found two hits of one example path in `docs/mcp.md`
   reachable only from the branch `c0195-mcp-server`. Delete that branch, or decide the hit (c0220, open
   question 2). Optionally run `make residue-history` with the private lists on the commit to be released
   and record it under c0220 task 1.3 and in the row `v0.6.0`.
3. Read the rows, the deferred tasks and the open changes of earlier releases, and write the verdict below.
   A verdict other than `pending` is refused by the guard while a row is `pending` or a placeholder stands.
4. Merge the pull request from `dev` to `main` (the release branch) when its checks pass.
5. Tag `v0.6.0` on the merge commit and push the tag (`docs/releasing.md`); the release workflow checks the
   versions and the changelog, scans the history, builds from its clean checkout of the tag, publishes both
   packages to PyPI and creates the GitHub Release.
6. Publish: read the release page (title `Fenolite 0.6.0`, latest, four files with PyPI's digests and
   `SHA256SUMS`).
7. Archive c0242 with the verdict, and the changes of the release in the order of "Archive order" when each
   can be.
8. Merge `main` into `dev`, and open `0.7.0.dev0` there.
