## Open rows

- **v0.2b item c0070.** Change c0070 is implemented and its oracle tests pass on 9.0.9 and 10.0.6, but it is
  not archived. Two things are open: a fix for a text overlap in the sheet of the blink example, in
  progress on its own branch, and task 6.2 of the change, in which the maintainer judges the rendered
  sheets by eye. No test can say that a sheet is readable. When both are done, the result of the row
  becomes `met`, or `met with a recorded limit` with its entry below, and this entry is removed.
- **c0043, the repeated sheet.** The schematic import instantiates a sheet that a sheet symbol repeats
  once, and does not annotate it: the components of the channels share one designator. On the public project set
  that has such a sheet, `check` reports `model.duplicate-ref` (`docs/evidence/altium-roundtrip.md`). The
  test named in the row proves the present behaviour, one instance read and a located note, not the
  designators. The design of c0043 leaves annotation files to v0.5b. A PCB document read on its own is
  not affected: its components take the designator the board shows (c0045).

## Recorded limits

- **v0.2a item 1, the examples.** The four KiCad examples have a clean ERC, and not all are proved in
  CI. `blink_2layer` and `board_40parts`, the two acceptance examples, are judged by the loop's `check`
  in the `routing` job on both majors. `blink_routed` passes ERC in
  `tests/kicad/export/test_manifest_oracle.py`, in `kicad-9` and `kicad-10`. `examples/blink_official`
  needs the official KiCad libraries, which no CI job installs: its ERC is asserted by
  `tests/libs/test_build_official.py::test_official_variant_passes_kicad_erc`,
  which runs where the libraries and `kicad-cli` are installed, so in the local `make check` only. It
  reports 0 violations on 10.0.6 (2026-10-06) and was not run on 9.0.9. Until that day it reported 29
  errors and 1 warning; its analog supply pins are connected and its 25 unused pins marked since.
- **v0.2a item 3, RT0 and RT1.** From `docs/evidence/kicad-schematic.md`: 125 of the 130 demo rows are
  read and pass both levels, bus rows and multi-instance rows included. 5 demo rows are older than the
  read floor (format `20231120`) and are not read; the acceptance list leaves them out with the use
  `sch-old`. The `kicad-9` job does not run `tests/corpus`; these two levels need no tool.
- **v0.2a item 3, RT2.** KiCad's ERC is not repeatable item by item, on 9.0.9 and on 10.0.6: for one
  violation it names one of the pins or labels involved, and not the same one in every run. Schematic
  RT2 therefore compares the kinds of violations, the sheet, type, severity and exclusion of each, with
  their counts (`H-K-ERC-REPEAT-2`, `H-K-ERC-RT2-2`; the rows that asked for equal items are refuted). It
  does not see a violation that only moves to another pin of the same sheet and type. On 10.0.6, 34 of 34
  projects are judged and hold, and on 9.0.9, 35 of 35; the 24 projects of the acceptance list hold on
  both. RT2 on 9.0.9 covers the projects of tag 9.0.9.1 whose sheets are at format `20250114` or older.
- **v0.2a item 4, `fmt`.** From `docs/evidence/kicad-fmt-identity.md`: 267 of the 269 `rt0` rows of the
  manifest are measured, and all 267 are a fixed point. The 2 rows tagged `heavy` are not run in CI. The
  test measures the canonical print that `fmt` writes and `fmt --check` compares with, file by file, not
  the command line.
- **v0.2b item 1, the update from the schematic.** No headless command runs KiCad's “Update PCB from
  Schematic”, so the test uses a stand-in that writes what the update was seen to write. `H-K-SCH-UPDATE`
  is `INFERRED`: one manual run by the maintainer in 10.0.6, on one board of three footprints, recorded
  above. No manual run was made on a project with module sheets.
- **v0.2b item 3, parity.** The project plan's reference counts (disconnected nets, missing connections,
  references on one side) are replaced by a comparison with KiCad's own parity test, as the roadmap
  says. Five KiCad types are compared (`missing_footprint`, `extra_footprint`, `duplicate_footprints`,
  `footprint_symbol_mismatch`, `net_conflict`) on the 14 demos of tag 10.0.6 that have a board and a
  schematic, and on the 5 readable demos of tag 9.0.9.1 that the `kicad-9` job fetches. Two entries of
  type `footprint_symbol_field_mismatch`, on 10.0.6 only, have no Fenolite code and are not compared.
- **Module sheets on 9.0.9.** On 9.0.9 one of the 25 generated designs reports one `pin_not_connected`
  fewer on its readable sheets than on the flat sheet, 24 against 25. The loss is inside KiCad's report:
  9.0.9 always reports 24 of the 25 open pins of that project, and which one it leaves out changes with
  content that has nothing to do with the pin (`docs/evidence/kicad-schematic.md`, “Hierarchy and
  wires”). The oracle test accepts a sheet tree that counts no violation type more often than the flat
  form. On 10.0.6 the counts are equal for all 26 designs.
- **Residue scan.** The residue scan of v0.2.0 ran with the public gate only: in CI and over the history
  (5403 blobs reachable from any ref, 0 hits, on 2026-10-06). The private gate was not run for v0.2.0.
- **c0040, the schematic reader.** No public schematic saved by Altium in the ASCII form is in the
  corpus, so `H-A-RD-SCH-ASCII` is not settled; the streams `PinTextData` and `PinSymbolLineWidth` stay
  opaque; `.Harness` files are not read; no multi-part library component is in the corpus.
- **c0041, the PCB reader.** One public document is skipped in the Linux job, because `kicad-cli` 10.0.6
  dies there in its own importer; it is compared on macOS only. Paste-layer pads, slotted hole sizes and
  some pad shapes are not compared with the importer.
- **c0042, project files.** Project files and output jobs are `CORPUS-VERIFIED`; rule files, stack-up
  files, the rule map and the scope grammar are `INFERRED`, and 44 of the 48 exported rule records have
  no neutral counterpart and are listed with a reason. The net scope numbers wait for an author report.
- **c0043, the import.** One of the five public project sets holds a heavy item and is not run in CI. Every
  set makes `check` exit 5 with error findings of the PCB reading: `model.body-height` on four of them,
  and `model.duplicate-ref` on the set with a repeated sheet (the defect under “Open rows”). 13 of the 20 import hypotheses are `INFERRED`. Nothing is
  written from an imported model.
- **c0044, the round trips.** RT-A0 is judged on 57 of 65 rows, RT-A1 holds on 65 of 65, and RT-A2 on 21
  of 21 builds. RT-A2 judges Fenolite's own builds only, and of them the circuit and the net classes: it
  says nothing about footprints, pads, tracks, vias or zones. The three levels are `INFERRED`.
- **c0045, equivalence.** The comparison with `kicad-cli pcb import` exists for 10.0 only. The Linux job
  compares six of the seven rows. 10 differences are excluded by five rules, each with its reason
  (`docs/evidence/equivalence-triangle.md`), and `H-G-EQ-L1` to `H-G-EQ-L4` stay `INFERRED`.
- **c0046, sheet templates.** Import only: no `.SchDot` is written, and its read hypotheses are
  `INFERRED`.
- **c0047, analyses.** Every reply of `analyze` is `INFERRED` or lower: Fenolite measures, ships no
  requirement value, and the user decides.

## Release build

The artefacts are built from the tagged commit in a clean checkout, never from the working tree: the
release workflow's checkout, a fresh clone of the tag, or a worktree of it.

```bash
git worktree add "$TMPDIR/fenolite-v0.2.0" v0.2.0
cd "$TMPDIR/fenolite-v0.2.0"
uv build --out-dir dist
uv build packaging/phenolite --out-dir dist
```

History scan, on 2026-10-06 at commit `f613c670`: `uv run python tools/residue/scan.py --history` read
5403 blobs with the public gate and reported 0 hits; the private gate was not run. The row `v0.2.0` of
`docs/evidence/residue-history.md` holds it. No build was rehearsed for this record: the `wheel` job
builds and installs both packages on every push.

## Maintainer's steps

Only the maintainer does these, in this order:

1. When the overlap fix of c0070 has landed and the renders are judged (task 6.2): update the row
   `c0070` of “Acceptance of v0.2b”, the second row of “Manual checks” and the entry under “Open rows”,
   and archive c0070.
2. Write the line for the CI run of the release candidate commit under “Runs and versions”.
3. Read the rows and write the verdict below. A verdict other than `pending` is refused by the guard
   while a row is `pending`.
4. Put the date of the tag in the heading `## [0.2.0]` of `CHANGELOG.md`.
5. Open the pull request from `dev` to `main` and merge it when its checks pass.
6. Tag `v0.2.0` on the merge commit.
7. Build from the tagged commit in a clean checkout: the commands of “Release build”, or the release
   workflow, which builds from its own checkout of the tag.
8. Publish: the GitHub Release starts the release workflow, which uploads both packages.
