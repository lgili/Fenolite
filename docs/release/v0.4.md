# Release record: v0.4

What the release `0.4.0` ships of v0.4, change by change: what each change ships, the test that proves
it, in which CI job, which of its tasks are still open and why. v0.4 has no acceptance block in
`docs/roadmap.md`: it is three groups of proposals (the agent track c0077 to c0081, board authoring c0096
to c0099, the complex board c0100 to c0120) and the changes written on `v04` after `0.3.0` (c0137, c0140,
c0141, c0145, c0152, c0153). A row says `ships`, `ships with deferred tasks` or `pending`. The verdict at
the end is the maintainer's. `tests/unit/test_release_record_v04.py` keeps this page honest about what
exists.

everything else ships. A task deferred by that decision is named under "Deferred to the next release";

## Maintainer's steps

Only the maintainer does these, or the coordinator at his word, in this order:

1. Read the checks of the release branch and of its pull request to `main`; the coordinator writes their
   runs in place of the placeholders above and closes the pending tasks whose proofs passed.
2. Read the first run of the `yardstick` job and write its row in `docs/evidence/yardstick.md`.
3. Confirm the residue waiver of c0110 ("Recorded limits").
4. Read the rows, the deferred tasks and the follow-ups, and write the verdict below. A verdict other than
   `pending` is refused by the guard while a row is `pending` or a placeholder stands.
5. Merge the pull request from `dev` to `main` (the release branch, which holds `v04`) when its checks pass.
6. Tag `v0.4.0` on the merge commit.
7. Build from the tagged commit in a clean checkout: the commands of "Release build", or the release
   workflow, which builds from its own checkout of the tag.
8. Publish: the GitHub Release starts the release workflow, which uploads both packages.
9. Archive c0154 with the verdict, and the changes of v0.4 in the order of "Archive order" when each can be.
10. Merge `main` into `dev`.
