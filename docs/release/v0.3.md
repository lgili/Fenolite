## Graduation of the Altium write

Change c0092 decides when an Altium write kind leaves `experimental` (design, decision 1): (a) the kind
has an own-readback test; (b) a kind with a model has the round-trip row of RT-A3 release-verified
(`H-A-VER-RTA3` is `CORPUS-VERIFIED`, `H-A-VER-RTA3-PRJ` is `INFERRED`); (c) every hypothesis id of its
write cell is release-verified (`ALTIUM-VERIFIED(kit)`, `KICAD-VERIFIED`, `ORACLE-VERIFIED`,
`CORPUS-VERIFIED`; an author report never counts); (d) at least one id is `ALTIUM-VERIFIED(kit)` from a
recorded run that is not stale. The design rules out graduation by decision.

**The maintainer's exception for 0.3.0.** No kit run is recorded. On 2026-10-08 the maintainer decided
that the kit did not change since his run of 2026-10-07 and is accepted as validated by that run for this
release. That decision is applied here as an exception to condition (d), for 0.3.0 only. It writes no run
record, no run id and no digest, and no row carries `ALTIUM-VERIFIED(kit)`
(`docs/evidence/altium-kit/README.md`).

**Revalidation owed after 0.3.0.** The kit run has to be made again on the kit that the tree builds and
recorded: `fenolite kit verify`, then `fenolite kit record --confirm`. The kit of this tree differs from the
folder of 2026-10-07 in its schematic files (changes c0134, c0144 and c0148); change c0148, which sets bit
0x20 on every pin of every schematic document and schematic library, needs the same revalidation.

The verdict per kind, counted on this tree from `docs/hypotheses.md` and the write cells of
`src/fenolite/backends/altium/claims.py` (c0092, task 4.1). The evidence of each kind is in its write
cell, listed in `docs/evidence/matrix.md`; the Altium checks of 2026-10-03 to 2026-10-08 are on
`docs/evidence/altium-pcb.md` and `docs/evidence/altium-schematic.md`.

## Maintainer's steps

Only the maintainer does these, or the coordinator at his word, in this order:

1. Done on 2026-10-08 by the coordinator: `main` (with the patch release 0.2.2, pull request #15) is
   merged into `dev` (`d2d2cf2`), and this branch is rebased onto it; the section `[0.2.2]` of
   `CHANGELOG.md` stands below `[0.3.0]`.
2. Read the checks of the pull request that brings the release to `main`: planned from `dev` to `main`,
   it is the pull request #16 from `release-0.3.0`, which holds `dev`; its CI run is the run of the
   release candidate commit, linked under "Runs and versions".
3. Read the rows, the graduation table and the list of what is not in 0.3.0, and write the verdict below.
   A verdict other than `pending` is refused by the guard while a row is `pending`.
4. Merge the pull request from `dev` to `main` when its checks pass.
5. Tag `v0.3.0` on the merge commit.
6. Build from the tagged commit in a clean checkout: the commands of "Release build", or the release
   workflow, which builds from its own checkout of the tag.
7. Publish: the GitHub Release starts the release workflow, which uploads both packages.
8. Merge `main` into `dev`.

## Verdict

publish it the same day: 0.3.0 ships with the Altium write experimental under the rule of c0092, and he

"Open rows" and "Not in 0.3.0"; only the release change c0150 is archived with this verdict.
