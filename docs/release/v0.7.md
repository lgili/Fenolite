# Release record: v0.7

What the release `0.7.0` ships, change by change: what each change ships, the test that proves it, in
which CI job, which of its tasks are still open and why. `0.7.0` is what `dev` and the integration batch
lote-29 implemented after `0.6.0`: circuits as code, the component, block and board libraries (c0243 to
c0282), the viewer (c0300 to c0305), the import and drawn-schematic fidelity work (c0311 to c0364), the
router track (c0365 to c0370), the conversion scope, Altium import and CI profiles (c0371 to c0389), the
Altium round trip through KiCad (c0401 to c0467), and the changes of earlier releases closed since `0.6.0`,
among them the v1.0 machinery of c0216 to c0220. A row says `ships`, `ships with deferred tasks` or
`pending`. The verdict at the end is the maintainer's. `tests/unit/test_release_record_v07.py` keeps this
page honest about what exists.

**The maintainer's decision of 2026-11-06.** He approved releasing `0.7.0` once the CI of lote-29 passes,
with what is implemented since `0.6.0`. c0468, the library generator families, is the next lote's. The rule
of his decision of 2026-10-08, kept on 2026-10-25 and 2026-10-29, still holds: what depends on his own tests
(runs in Altium Designer, KiCad GUI saves made by him, a run of a real AI agent, his own MCP client) is
deferred, the code of its change ships, and no evidence label is raised for it.

that are not ticked on the release branch. A change of an earlier release has a row only when code changed

## Release build

The artefacts are built from the tagged commit in a clean checkout, never from the working tree: the
release workflow's checkout (`.github/workflows/release.yml`, change c0221), a fresh clone of the tag, or a
worktree of it.

```bash
git worktree add "$TMPDIR/fenolite-v0.7.0" v0.7.0
cd "$TMPDIR/fenolite-v0.7.0"
uv run --no-project python tools/release.py check --tag v0.7.0
uv build --out-dir dist
uv build packaging/phenolite --out-dir dist
```
